# Land production-like Kind topology before the resilience-test harness; leave Postgres single-instance

This phase moves `rest-service`, `email-service`, and Kafka onto Kind with a genuinely HA-shaped topology — 3 Kafka brokers, 2 replicas per app service, pod anti-affinity, PodDisruptionBudgets — even though no chaos/failure-injection tests exist yet to exercise it. The topology is deliberately built ahead of the tests that will validate it, as groundwork for a follow-up issue covering pod/node-loss and network-partition testing. Postgres stays a single instance with no replication: Postgres HA (consensus/failover tooling) is a substantial project of its own, orthogonal to what this phase and its planned follow-up test, and is out of scope until a dedicated issue addresses it.

**Consequences**: a future reader will see replica counts and anti-affinity rules with nothing yet asserting they work — that's intentional, not premature complexity. Any resilience test added later must treat Postgres downtime as an accepted, untested failure mode rather than something the suite verifies recovery from; Kafka Connect also stays single-instance until Postgres HA exists, since a second Connect worker would only be a warm standby with no real failover story until Postgres itself can be failed over to.
